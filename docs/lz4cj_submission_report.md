## 一、项目概述

### 1. 项目一句话定位

本作品是业界广泛使用的 LZ4 高性能无损压缩库（上游 v1.10.0）的**纯仓颉完整重实现**（零 FFI、零 C 依赖），覆盖 block 压缩/解压、流式与字典、HC 高压缩（级别 1–12）、LZ4 Frame 帧格式（压缩+解压）全量非弃用 API（74 函数 + 常量族），**压缩输出与 C 实现逐字节一致**，与官方 stdx.compress（DEFLATE 系，压缩率优先）互补，为仓颉生态补齐 LZ4 系高速无损压缩能力与 C lz4 生态数据互通能力，适用于服务端数据存储压缩、网络传输数据量削减、客户端本地数据持久化等高吞吐场景。

### 2. 项目开发背景

- **LZ4 是事实标准，但仓颉生态此前无 LZ4 算法族实现**。LZ4 以极快的压缩/解压速度著称，被 Linux 内核、ZFS、Redis、Kafka、RocksDB 等广泛采用，是数据压缩领域的基础组件；但上游仅有 C 实现。官方拓展标准库 stdx.compress 提供 DEFLATE 系压缩（基于开源 zlib，deflate-raw/gzip 两种格式 + tar 归档），属压缩率优先的中低速算法族——LZ4 所代表的速度优先算法族及其 block/帧数据格式此前在仓颉生态为空白。
- **FFI 绑定路线不可行/不优雅**。通过 FFI 封装 C 库需要为每个目标平台交叉编译、分发二进制，部署链路复杂，且无法享受仓颉运行时的内存安全与 GC 模型；纯仓颉实现可随仓颉工具链一次构建、随处运行。
- **仓颉开发者的真实痛点**。服务端日志/KV 存储/消息队列、客户端缓存与配置快照、IoT 数据上报等高频热路径对压缩吞吐敏感，退而使用 DEFLATE 系速度不匹配（解压吞吐通常低约一个量级），或只能手写简陋的 RLE/字典编码、乃至放弃压缩；且 C 侧 lz4 存量压缩数据无法在仓颉侧直接消费。
- **移植保真度是难点也是价值点**。LZ4 压缩输出取决于哈希步进、匹配确认、token 编码等大量实现细节，一般"语义等价"重写会导致输出与 C 不同，无法与既有数据互操作、无法用 C 语料做回归验证。本项目以"逐字节一致"为强校验目标，使仓颉版产物可直接被 C lz4 工具解压、可直接消费 C 侧存量压缩数据。

### 3. 项目核心目标

- **基础功能目标（已全部达成）**：
  1. 上游四文件全量移植：`lz4.c`（block 压缩/解压/流式/字典）、`lz4hc.c`（HC 三策略、级别 1–12）、`lz4frame.c`（帧压缩 + 帧解压全量）、`xxhash.c`（XXH32/XXH64，internal）——非弃用 API 全量 74 函数 + 常量族；
  2. API 命名与 C 头文件**逐字一致**（`LZ4_compress_default`、`LZ4F_max64KB`……），C 用户零学习成本迁移；
  3. 同一套源码在仓颉 LTS-1.0.5 与 STS-1.2.0 双工具链下编译并全部测试通过。
- **进阶创新目标（已全部达成）**：
  1. 确定性条件下压缩输出与 C 实现**逐字节一致**（489 行 golden 数据全矩阵 + 双版本基线重验零差异）；
  2. 工程化质量：156 项测试在双工具链下全部通过、库源码行覆盖 97.44%、4200+ 模糊测试种子零异常、零警告构建、下游依赖一键验收；
  3. 完整开发者文档：README API 对照表、使用示例、设计文档、逐里程碑 CHANGELOG。

## 二、需求分析与适用人群

### 1. 目标用户精准定位

- **仓颉服务端开发者/团队**：需要对消息、日志、KV value 做透明压缩以降低存储与带宽成本的服务端项目；
- **鸿蒙应用/客户端开发团队**：本地快照、缓存、配置档等持久化数据的压缩存储（客户端场景，纯仓颉实现、无 NDK 依赖）；
- **IoT/边缘开发者**：设备端上报数据的轻量压缩（LZ4 解压极快、资源占用低）；
- **学生与研究者**：学习工业级压缩算法实现、仓颉系统级编程（unsafe/CPointer/性能工程）的参考范本。

## 三、作品核心能力与功能设计

### 1. 基础通用能力

**（1）一站式块压缩/解压**
- 功能介绍：`LZ4_compress_default / fast / fast_extState(+fastReset) / destSize(_extState)` 与 `LZ4_decompress_safe(_partial)(_usingDict)` 等完整函数族，含 `LZ4_compressBound` 界限计算。
- 适用开发场景：内存数据块的单次压缩/解压，如 KV value、消息体、RPC 帧。
- 调用方式简述：`let c = LZ4_compress_default(src, n, dst, bound)`；解压 `LZ4_decompress_safe(dst, c, back, n)`，错误返回负位置编码（同 C）。
- 实现效果与价值：开箱即用的内存压缩原语，destSize 支持"压缩到指定预算内"（返回 `(ret, srcConsumed)` 元组）。

**（2）流式压缩/解压（字典 · 续用 · 滚动解码）**
- 功能介绍：`LZ4_createStream/freeStream/resetStream(+fast)`、`loadDict(+Slow)`、`attach_dictionary`、`compress_fast_continue`、`saveDict` 与流式解码 `createStreamDecode/setStreamDecode/decompress_safe_continue/decoderRingBufferSize`，真实 `prepareTable` 表保留语义与四字典模式压缩核心。
- 适用开发场景：分块到达的数据流（日志流、网络流）、跨块字典延续、环缓冲滚动解码。
- 调用方式简述：缓冲-位置对 `(buf, idx)` 承载 C 滚动指针：`LZ4_compress_fast_continue(srcBuf, srcIdx, ...)`。
- 实现效果与价值：任意切分粒度的流式处理能力，跨块压缩率不退化，C 指针语义完整落地。

**（3）HC 高压缩模式（级别 1–12 全量）**
- 功能介绍：`lz4hc.c` 非弃用 17 函数：三策略核心 LZ4MID（lv1–2）/ hashChain（lv3–9）/ optimal 最优解析（lv10–12）+ `favorDecompressionSpeed`；one-shot / extState(+fastReset) / destSize / 流式 `loadDictHC / attach / continue(+destSize) / saveDictHC`。
- 适用开发场景：压缩率优先的冷数据存储、归档，需在压缩率与解压速度间权衡的场景。
- 调用方式简述：`LZ4_compress_HC(src, n, dst, bound, 9)`；级别常量 `LZ4HC_CLEVEL_MIN/DEFAULT/OPT_MIN/MAX` 与 C 逐字一致。
- 实现效果与价值：仓颉生态首个 LZ4 全级别高压缩实现，levels 1–12 全部与 C 输出逐字节一致。

**（4）LZ4 Frame 帧格式（压缩 + 解压全量）**
- 功能介绍：`lz4frame.c` 全量 28 函数——压缩侧 21（版本/错误/界限、cctx 生命周期、`compressBegin(+usingDict/+usingCDict)`、`compressUpdate/uncompressedUpdate/flush/compressEnd`、一次性 `compressFrame(+usingCDict)`、`LZ4F_CDict` 预消化字典）+ 解压侧 7（dctx 生命周期、`headerSize/getFrameInfo`、`decompress(+usingDict)`）；14-stage 分片续传状态机、块/内容 XXH32 校验和、skippable 跳帧、帧拼接。
- 适用开发场景：文件/落盘格式、跨端传输的标准帧格式（可被 C lz4 CLI 直接解压）、字典分发场景（CDict）。
- 调用方式简述：一次性 `LZ4F_compressFrame(...)`；流式 Begin/Update/End 三段式；解压返回 `(ret, srcConsumed, dstWritten)` 三元组，`ret` 兼作下次调用的建议字节数（hint）。
- 实现效果与价值：与 C lz4 生态互联互通的落盘/传输格式能力，任意分片续传（随机切分 × 容量阶梯全矩阵验证）。

**（5）XXH32/XXH64 校验和（internal）**
- 功能介绍：与上游同构的 XXH32/XXH64 两套实现（one-shot + 流式 state），官方向量 + C 交叉验证；供 frame 校验和内部使用，XXH64 备用。
- 适用开发场景：帧校验和、数据完整性校验。
- 调用方式简述：库内 internal，经 frame API 间接使用；如需对外暴露为后续版本增量。
- 实现效果与价值：补齐 LZ4 frame 依赖的校验和底座，独立双实现避免泛型装箱开销。

### 2. 创新特色能力

**（1）创新点一：压缩输出与 C 实现逐字节一致（移植保真度强校验）**
- 创新详情：以"确定性条件下压缩输出与 C 逐字节相同"为硬性验收——489 行 golden 数据矩阵（15 类语料 × 全参数交叉：block/HC levels 1–12/frame 五枚举全组合/字典/destSize/流式 27 变体等）由上游 C 源编译生成，仓颉侧再压缩逐字节比对；并对上游 dev（0774d055）与 v1.10.0 发布版**双基线重验零差异**。哈希步进、匹配确认方向、token 进位、最后 5 字节 literal 规则等保真点逐一验证并固化。
- 相较于同类仓颉库的核心优势：一般"语义等价"实现的压缩产物无法与存量 lz4 生态互操作、无法用 C 语料回归验证；本库产物可被标准 lz4 CLI 解压，可直接消费 C 侧数据，升级对照审查成本最低。

**（2）创新点二：零 FFI 纯仓颉 + C API 命名逐字一致的接口设计**
- 创新详情：无任何 C 绑定与第三方依赖；函数/类型/常量/枚举成员名与 C 头文件逐字相同，仅以四条全局统一规则适配仓颉承载差异——① in/out 指针 → 返回值元组；② 可空指针 → `Option<T>`；③ 指针前移 → 具名必传参数 `offset!`；④ 滚动/流式续用指针 → `(buf, idx)` 位置对。全部偏离在 README API 对照表逐条登记（如 C 指针相等分派在仓颉无引用同一性比较下的等价策略、`decompress_fast` 不安全 API 不移植等）。
- 相较于同类仓颉库的核心优势：C 背景开发者零学习成本；与上游 diff 审查、后续升级同步成本最低；接口契约文档化程度远超一般三方库。

**（3）创新点三：双工具链（LTS-1.0.5 / STS-1.2.0）同源构建、测试全部通过**
- 创新详情：源码约束在两版本共同语言子集，任何提交必须双工具链构建 + 全量测试通过；`setup_env.sh/build_and_test.sh` 一键环境与验证，`verify_downstream.sh` 以临时下游工程验证 path 依赖真实可用性。
- 相较于同类仓颉库的核心优势：多数三方库仅覆盖单一工具链版本；本库同时服务存量 LTS 用户与 STS 早期采用者，并以发布分支/tag（`v0.9.0-lt` / `v0.9.0-st`）提供确定性制品。

**（4）创新点四：工业级验证体系（黄金语料 + 模糊测试 + 覆盖率门禁）**
- 创新详情：156 项测试；库源码行覆盖 97.44%（common/xxhash/datagen 100%）；4200+ 模糊测试种子（解压 3000 + 流式 320 + HC 420 + frame 压缩 240 + frame 解压 300，含随机切分、帧拼接、损坏输入三型，断言错误码而非异常逃逸）；golden 语料可本地再生（生成脚本 + 门禁校验 + 内嵌常量摘要自足校验）；零警告构建。
- 相较于同类仓颉库的核心优势：验证深度对标上游 C 项目测试范式（上游 frametest 分片续传的已知陷阱以清单方式移植），可达未覆盖行逐行归类裁定，工程可信度可审计。

## 四、仓颉语言核心特性应用

**1. 应用仓颉特性 1：`CPointer` + `unsafe` 域的冷/热路径分界**
- 技术实现与封装逻辑：公开 API 入口、参数校验、frame 装配等冷路径用 `Array<UInt8>` 安全索引；block/HC/解压内层循环、哈希表访问、序列复制等热路径经 `acquireArrayRawData` 一次性取得 `CPointer<UInt8>` 手工寻址（非对齐读写 `MEM_read/write16/32/64`、`wildCopy8` 野复制、交叠复制），acquire → 操作 → release 严格在同一 `unsafe {}` 域内完成且域内零分配（保证 GC 不移动对象、裸指针有效），域内沿用 C 的显式边界检查。
- 落地优势与效果：在保留仓颉安全模型的同时获得接近 C 的内存访问形态；配合 `-O2`（cjpm.toml 固化，`-O0`→`-O2` 热循环实测 7~23 倍差距），使压缩库这类计算密集场景在仓颉上工程可行。

**2. 应用仓颉特性 2：元组多返回值承载 C in/out 指针出参**
- 技术实现与封装逻辑：仓颉无引用出参，C 的 `srcSizePtr/dstSizePtr` 类参数统一并入返回值元组：`LZ4_compress_destSize(...) → (ret, srcConsumed)`、`LZ4F_decompress(...) → (ret, srcConsumed, dstWritten)`、`LZ4F_getFrameInfo(...) → (code, frameInfo, srcConsumed)`，错误契约恒 `(code, 0, 0)`。
- 落地优势与效果：接口无副作用、无未初始化出参陷阱，调用方模式匹配一次解构，比 C 的指针出参更安全且信息不丢失。

**3. 应用仓颉特性 3：`Option<T>` 可空类型承载 C NULL 指针语义**
- 技术实现与封装逻辑：C 可空结构体指针（`preferencesPtr`、`dOptPtr` 等）映射为 `Option<T>`，`None` 代入 C 的 MEM_INIT 零值语义；空缓冲 + 容量 0 等价 `NULL+0` 守卫路径。
- 落地优势与效果：空值语义显式进入类型系统，调用方编译期即知参数可空，消除 C 生态最常见的 NULL 解引用类缺陷面。

**4. 应用仓颉特性 4：class + GC 承载 C opaque 状态对象**
- 技术实现与封装逻辑：`LZ4_stream_t / LZ4_streamDecode_t / LZ4_streamHC_t / LZ4F_cctx / LZ4F_dctx / LZ4F_CDict` 等 C 堆分配 + `void*` 别名访问的 opaque 上下文统一建模为仓颉 class，字段与上游结构体逐字段对应；"以用户提供的裸缓冲充当状态对象"的 C API（`fast_extState` 族）参数类型改为对应状态类实例；GC 取代 create/free 手动内存管理。
- 落地优势与效果：彻底消除内存泄漏/悬挂指针/双重释放类问题；状态生命周期由运行时保障，接口更符合仓颉惯例。

**5. 应用仓颉特性 5：包可见性 `internal` 实现封装边界**
- 技术实现与封装逻辑：xxhash（XXH32/XXH64）、datagen、common 工具层均以 `internal` 可见性隐藏，仅 frame 所需路径内部使用；对外仅暴露 lz4.h/lz4hc.h/lz4frame.h 对应 API。
- 落地优势与效果：公共 API 面与上游头文件严格对齐，内部实现细节（如 `freeState` 归零语义偏离）不污染下游命名空间。

**6. 应用仓颉特性 6：`--int-overflow=wrapping` 整数回绕语义与静态类型宽度区分**
- 技术实现与封装逻辑：LZ4 位置哈希依赖 32 位乘法回绕（`(seq * 2654435761) >> shift`），包级统一开启 wrapping 溢出语义；C `int/unsigned` → `Int32/UInt32`、`size_t` → `Int64` 逐表达式对应移植，不做优化性改写。
- 落地优势与效果：以编译选项精确复刻 C 整数行为，避免默认溢出检查在热点路径抛异常或拖慢性能，是逐字节一致的必要条件之一。

**开发技术栈与工具**：开发语言仓颉（Cangjie，LTS-1.0.5 / STS-1.2.0 双 SDK）；构建 cjpm + cjc（`--int-overflow=wrapping -O2 -Woff unused -Woff parser`，静态库）；版本管理 Git；golden 语料生成 cc（编译上游 C 源作对照 harness）；**零第三方运行时依赖**（纯仓颉标准库）；适配 x86_64 / aarch64 Linux。

## 五、库性能与兼容性设计

### 1. 性能优化设计

- **编译层**：cjpm.toml 固化 `-O2`（仓颉默认 `-O0`，热循环差距实测 7~23 倍，工具链升级时以 bench 防回归）；`--int-overflow=wrapping` 消除热点溢出检查开销。
- **代码层**：冷/热路径分界（见特性 1）——热路径 CPointer 手工寻址 + 沿用 C 的粗对齐批量比较（8 字节步进）与野复制；泛型合并 XXH32/64 经双工具链实验证实在 `-O0` 下装箱分派慢 3~35 倍、`-O2` 下仅能持平，故采用双特化实现。
- **实测基线（与 C 对照，best-of-3 同机同口径）**：吞吐为 C 的 0.02–0.6x。差距结构性来源：仓颉数组安全层/GC/调用开销 vs C 裸内存 + SIMD memcpy。**性能裁定（已形成书面结论）**：单点微调收益远小于结构性差距且危及"逐字节一致"保真资产，裁定库源码冻结不做性能优化；`benchAllTest` 作为数量级劣化的非回归监控（`LZ4_SKIP_BENCH=1` 可跳过）。后续版本可探索 unsafe 域内 SIMD。
- **LZ4 解压速度本身极快**（C 版即数 GB/s 量级），0.02–0.6x 的仓颉实现在多数业务场景（日志、KV、配置）仍是可用的工程吞吐。

### 2. 兼容性设计

- **仓颉语言版本**：同一套源码同时支持 LTS-1.0.5 与 STS-1.2.0（共同语言子集约束，无版本条件编译）；发布分支 `lz4_lt_1.0.5` / `lz4_st_1.2.0` 与 tag `v0.9.0-lt` / `v0.9.0-st`。
- **数据格式兼容**：LZ4 block 格式与 Frame v1.0 规格（魔数/FLG-BD 头/XXH32 校验和/skippable 帧）；压缩产物与 C 逐字节一致，可被 v1.10.0 及以后的标准 lz4 工具解压；解压侧包含 v1.10.0 之后上游官方 OOB/边界修复（损坏输入行为更严格、可复现，合法输入输出一致）。
- **平台**：x86_64 / aarch64（非对齐访问按小端 CPointer 语义，已备按字节组装回退预案）；服务端/客户端场景均适用。
- **下游接入兼容**：`cjpm.toml` 本地 path 依赖即用；`scripts/verify_downstream.sh` 双工具链一键验收下游真实构建。

### 3. 稳定性与容错设计

- **错误语义与 C 逐字对齐**：block 解压错误为负位置编码 `-(ip)-1`，尺寸校验 -1；frame 侧保持 `LZ4F_errorCode_t = Int64` 数值错误码模式，配套 `LZ4F_isError/getErrorName/getErrorCode`，不改用异常（调用方按 C 习惯先查 `isError`）。
- **不移植不安全 API**：`LZ4_decompress_fast` 族（不校验输入边界的快路径）在仓颉安全模型下无忠实等价物，明确不提供（ASAN 实证该路径合法输入亦可 OOB），引导使用 `decompress_safe`。
- **模糊测试保障**：4200+ 种子覆盖随机数据/随机切分流式喂入/帧拼接/损坏三型（token 翻转、截断、长度溢出），断言负错误码返回而非异常逃逸，全部零异常。
- **防御性设计**：理论上不可达路径以防御性断言 + 注释登记；GC 陈旧读现象经最小复现程序 10 轮测试零复现，已调查关闭；`virgin-attach` 上游 UB 路径（C 侧 NULL 解引用崩溃）做防御性回退不复刻。

## 六、使用说明与落地场景

### 1. 快速接入说明

```toml
# 下游 cjpm.toml —— 一行接入，零传递依赖
[dependencies]
  lz4 = { path = "<lz4cj 路径>" }
```

```cangjie
package my_app
import lz4.*

main() {
    let src = ...                       // 原始数据(Array<UInt8>)与长度 n
    let bound = LZ4_compressBound(n)    // 容量上界
    let dst = Array<UInt8>(Int64(bound), {_ => 0u8})
    let c = LZ4_compress_default(src, n, dst, bound)   // 压缩
    // ... 存储或传输 dst[0..c) ...
    let back = Array<UInt8>(Int64(n), {_ => 0u8})
    let d = LZ4_decompress_safe(dst, c, back, n)       // 解压
}
```

构建 `scripts/build_and_test.sh both`；下游验收 `scripts/verify_downstream.sh`（block/HC/frame 三路往返 + 固定值断言，双工具链均通过）。零侵入：不要求改造调用方数据结构，任何 `Array<UInt8>` + 长度即可。

### 2. 落地应用场景

- **服务端项目开发**：日志压缩落盘、KV 存储透明压缩（Redis-style value 压缩）、RPC/消息负载缩减、快照/备份归档（HC 高级别 + Frame 格式 + 校验和）；可与 stdx.compress.tar 组合构建 tar.lz4 归档压缩工作流；
- **鸿蒙应用/元服务开发**：本地缓存、草稿箱快照、配置与资源包压缩（纯仓颉客户端场景，无 NDK 依赖）；
- **IoT 设备程序开发**：传感数据批量上报压缩（LZ4 解压端极快，适合设备端压缩、云端解压的架构）；
- **校园项目实训**：数据结构/算法课程中序列化数据的压缩实践，仓颉系统级编程教学样本（unsafe 域、CPointer、性能工程范式）；
- **企业级项目迭代**：C 存量 LZ4 数据（含 lz4 CLI 产物）向仓颉平台迁移时的直接解压能力（格式互通）。

### 3. 核心价值

- **开发价值**：为仓颉开发者提供与 C lz4 逐字节兼容的压缩/解压/流式/帧全能力，消除重复开发；API 命名与 C 一致，存量 C/其他语言使用者可平滑迁移。
- **生态价值**：补齐仓颉生态 LZ4 系高速压缩品类空白，与官方 stdx.compress（DEFLATE 系）互补成对、共同覆盖"速度优先/压缩率优先"两类需求（BSD-2-Clause 开源，与上游许可一致）；产物/数据与全球 lz4 生态互通；为后续仓颉上层存储/序列化框架（如持久化引擎、列存、RPC 框架压缩层）提供底座。
- **创新价值**：验证了"工业级 C 系统库向仓颉高保真移植"的完整方法论（保真点清单 + golden 交叉验证 + 指针语义等价策略），为同类库（zstd、snappy 等）移植提供可复制范式。
